# Experiment：検索結果を追跡可能なコンテキスト層にする

このカードは myRAG のローカル検索実験を記録する。現在の結論は、文書、インデックス版、検索実行を分けて管理し、ソース付きの証拠チャンクをハイブリッド検索で返せるということだ。Anomalo Harness のコンテキスト組み立てに向けた、検査可能な資料層になる。

## 検証課題

Agent が短期的なセッションコンテキストだけに依存すると、検索した資料を再利用しにくく、回答の出典も説明しにくい。テキストをそのままプロンプトへ入れるのではなく、文書取込、分割、インデックス、検索を再実行できるワークフローにできるかを検証した。

## 方法

myRAG はプロジェクトごとに文書、不変の設定版、インデックス状態、検索実行を保存する。第一版では長さによる再帰分割と自然段落の意味分割を使い、OpenRouter embeddings と SQLite FTS5 のキーワード検索を RRF で統合する。任意の階層的な説明インデックスでは、元チャンク、チャンク説明、文書説明のベクトルを別々に保存する。文書ベクトルはソフトなルーティング加点だけに使い、元チャンクを証拠として残す。REST API はプロジェクト作成、文書取込、再インデックス、プロジェクト検索、主データベース検索を提供する。

## 結果

API とテストでは、「プロジェクト作成 → 資料取込 → 設定保存 → 再インデックス → 検索」の流れを確認している。テスト結果には content vector と keyword の両方のヒットが含まれ、チャンクのソースと順位も保持される。この実験は追跡可能な検索証拠を提供するが、現在のコード上の証拠は独立した myRAG ワークベンチを示すものだ。Anomalo リポジトリはまだ RAG を Harness の進化目標として扱っているため、同じリポジトリで直接接続が完了したとは書かない。

## 制約

第一版は英語資料を対象とし、トークナイザーは `none` のままだ。ベクトル構築には OpenRouter API key が必要で、説明生成を有効にすると chat と embedding の呼び出しが増える。README では東アジア言語のトークナイザーと MCP を後続実験としているため、このカードは RAG 検索の基盤を検証するもので、完全な MCP データベースサービスではない。

## その後への影響

RAG により、Harness の「長期資料」に観測可能なインターフェースができた。コンテキストを組み立てる前に、Agent はチャンク、ソース、ヒット種別を受け取れる。次は Anomalo と myRAG の接続方法を決め、完成したインデックスを回答品質と同一視せず、実タスクで検索品質を評価することだ。
