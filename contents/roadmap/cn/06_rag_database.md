# Experiment：让检索结果成为可追溯上下文

RAG Database 这张卡片记录了 myRAG 的本地检索实验。当前结论是：文档、索引版本和检索记录可以被拆开管理，再用混合召回返回带来源的证据区块，为 Anomalo Harness 的上下文组装提供可检查的资料层。

## 问题

如果 Agent 只能依赖会话里的短期上下文，资料检索就很难复用，也很难解释答案来自哪里。问题是如何把文档写入、切分、索引和召回变成一个能重复检查的工作流，而不是只把文本塞进提示词。

## 方法

myRAG 为每个项目保存文档、不可变配置版本、索引状态和检索记录。第一版提供按长度递归切分与按自然段语义切分，使用 OpenRouter embeddings 和 SQLite FTS5 关键词召回，再用 RRF 合并候选。可选的分层描述索引会分别保存区块原文、区块描述和文档描述向量；文档向量只作为软路由加分，原文区块仍是证据。REST API 覆盖创建项目、导入文档、重建索引、项目检索和主数据库检索。

## 结果

API 流程和测试已经覆盖“创建项目 → 导入资料 → 保存配置 → 重建索引 → 检索”的闭环。测试结果同时包含 content vector 和 keyword 命中，并保留区块来源与排名信息。这个实验提供了可追溯的检索证据，但当前代码证据描述的是独立的 myRAG 工作台；Anomalo 仓库仍把 RAG 视为 Harness 的演化目标，不能据此宣称已经完成同仓库直连。

## 局限

第一版以英文资料为目标，分词器仍是 `none`；构建向量需要 OpenRouter API key，描述生成还会增加 chat 和 embedding 调用。README 把东亚语言分词器和 MCP 列为后续实验，因此这张卡片验证的是 RAG 检索基础，不是完整的 MCP 数据库服务。

## 后续影响

RAG 让 Harness 的“长期资料”有了可观察的接口：Agent 可以在上下文组装前先获得区块、来源和召回类型。下一步仍应明确 Anomalo 与 myRAG 的连接方式，并用真实任务评估召回质量，而不是把索引完成等同于回答质量。
