# Experiment：从向量召回走向 Agentic 搜索

RAG Database 这次更新探索搜索方式的变化：从按向量相似度返回区块，走向更接近人查资料习惯的 Agentic 搜索。Agent 根据任务浏览目录、选择关键词、阅读原文，再根据获得的信息决定是否补搜。myRAG 当前已实现这套流程需要的浏览、搜索和读取接口，Agent 自主编排与效果评估仍待接入。

## 问题

人查书会看目录，寻找术语，读相关章节，再根据内容调整问题。我想测试 Agent 能否采用类似的探索过程，让搜索策略随着阅读推进。向量、关键词和描述索引由内部处理，对外提供的是可供 Agent 操作的资料入口。

这也是对工业界 Agentic 搜索实践的一次本地试验。Anthropic 的[上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)介绍了通过工具按需加载资料、逐步发现上下文的做法。本实验要检验这种方式如何适用于文档与案例库，旧的原文向量召回保留作对照。

## 方法

myRAG 先建立可探索的资料结构。目录与章节模式保留 Markdown 标题的层次、顺序和原文字符范围；没有明确目录的纯文本只建立一个文档节点。对外的 REST API 分别提供目录浏览、搜索与原文读取。搜索返回线索和摘录，读取可以扩展到子章节并分页返回，文档、章节和索引 ID 保留来源定位。

Indexer 在内部准备章节关键词、描述和假设检索目的，例如“修改资料后怎样让搜索生效”。开启 AI 卡片后，父章节参考子章节描述，文档整体描述保存在根节点，并且只对描述和目的做向量化。SQLite FTS5 保留标题、词语和原文的文字搜索。关键词、语义和混合方式是内部召回手段，实验界面仍允许分别观察；离线关键词模式无需模型凭据。

用户案例采用另一种组织方式：案例概况加事件时间线。导入时保留原始事件记录，并区分观察、操作、推测和结果；没有确认的原因或处理结果保持未知。案例快照沿用同一套搜索和读取接口。

计划中的 Agent 循环是“发现 → 阅读 → 判断 → 补搜”，何时继续由任务与已读内容决定。这延续了 Search & Fetch 卡片的分工：搜索发现线索，读取补足证据。主检索入口固定到选定的索引版本，为比较不同搜索流程保留一致的资料范围。

## 结果

15 个离线测试通过，覆盖目录层次、中文关键词、原文定位与分页、案例记录、主索引固定，以及描述和目的向量的召回流程。模型相关测试使用替身，验证了原文没有进入向量化，并能通过目的向量召回措辞不同的查询；它没有验证真实模型生成的目的是否准确。

前端类型检查和构建通过，本机界面也完成了导入、浏览、搜索和读取验证。当前成果是 Agentic 搜索所需的资料与工具基础，AnomaloHaris 尚未接入，不能把人工操作跑通写成 Agent 已经完成自主搜索。

## 局限

目录解析目前只处理 Markdown 标题，中文和日文搜索使用简单的二元字串分词。卡片描述可能遗漏细节，假设检索目的也可能偏离资料能回答的问题。向量排名表示相似度，不能当作答案可信度。

真实模型的卡片质量、召回率和成本尚未评估。case 只支持快照导入，没有事件追加或更正；重排、增量索引和复杂文档解析也尚未实现。Agent 多轮探索还可能增加延迟、调用费用或走向无关线索，当前没有证明它比单次向量召回更有效。

## 后续影响

下一步是把浏览、搜索和读取接口接入 AnomaloHaris，运行由 Agent 决定步骤的搜索循环。用同一组文档和案例问题，对比单次召回与主动阅读、补搜的过程，检查证据是否充分、漏检是否减少，以及延迟、工具调用次数和成本。向量等技术继续作为内部索引与召回选项，实验重点放在 Agent 怎样寻找和使用资料。
