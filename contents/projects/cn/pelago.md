# Pelago：从测试证据演进到设计与验证

Pelago 是安装在现有 Git 项目内的设计与验证工具，用于保存需求、设计、PCL 和执行证据。当前 v0.1.0 已实现本地 CLI、审阅工作台和宿主 Agent 工作流，界面与审阅细节仍在开发中。

## 背景与目标

TeaForge 将自动化测试转换为 PCL、覆盖率报告和可审计证据。Pelago 延续了这套工程表达，并将关注点前移到实现之前：先明确需求和设计预期，再编写测试，最后用执行结果检查约定是否成立。

这一演进要解决的问题是设计与验证之间的对应关系。测试通过需要能追溯到具体要求，修改后的证据需要能区分设计版本，子任务完成也需要与整体交付分开判断。

Pelago 伴随其他项目的开发而诞生。我把它看作开发过程的 Side B：把共同开发中形成的设计与检查方法整理成独立工具。它延续 TeaForge 的想法，但不属于 AnomaloHaris 的演进分支。

## 设计与实现

Pelago 将运行时、CLI、工作台和 Skill 安装到宿主项目的 `.pelago/` 目录。宿主 Agent 通过 CLI 创建和修订档案，工作台用于审阅设计、PCL 与证据，以及维护项目的图表要求和测试规则。

一个 Issue 对应一份内嵌 JSON 的 HTML 档案。设计对象使用稳定 ID，引用记录设计版本；修改保留历史，写入检查版本冲突。结构化数据与可阅读文档随宿主 Git 保存和同步。

工作流按设计确认、测试准备、实现、验证和审查推进。设计预期与运行证据分别保存，设计或测试变化会影响后续证据的有效性。父 Issue 保留整体场景的验证责任，子 Issue 的完成状态不产生父级验证结果。

## 当前能力

- 保存 Feature 与 Bugfix 的原始需求、设计对象、文件计划和 Mermaid 图表；Bugfix 记录复现、原因调查及 As-Is／To-Be。
- 使用 PCL（Program Check List）描述输入、操作、预期输出和检查项，并关联需求与设计。用例区分 N 正常、E 异常、I 边界，判定矩阵每页最多 25 列。
- 通过本地 CLI 记录设计确认、测试准备、执行结果和宿主 Agent 审查；档案修订支持版本冲突检查和历史保存。
- 按带版本的引用合并展示 Bug 关联的原有用例与新增用例，标出新增行和判定列，并保留来源与执行状态。
- 提供中文、日文和英文的界面、PCL 标签与导出标题，支持自包含 HTML 和可选 PDF 导出。作者原文与执行日志不自动翻译。

## 边界与取舍

Pelago 不提供模型 API。设计、测试和审查由宿主 Agent 完成，审查报告作为证据导入。确认和接受记录需要真实用户授权，工具尚未提供审查身份认证。

PCL 合表用于审阅上下文，不自动执行原有用例，也不把原 Issue 的通过记录计为本次回归通过。测试通过数不能证明输入覆盖或代码覆盖，仍需检查对应的测试与报告。

协作依赖宿主 Git，当前不提供跨克隆实时共同编辑或共享 SQLite 存储。PDF 导出需要额外的 Playwright 与浏览器环境。TeaForge 报告的直接导入、所有技术栈的集成验证尚未提供。

## 状态与下一步

Pelago 当前处于 v0.1.0 开发阶段，档案、流程和审阅界面已有实现。它延续 TeaForge 的想法，但当前版本的完成状态与验证范围需要独立判断。

下一步是根据实际审阅反馈继续打磨文档层级、头部信息、操作位置和长测试表的阅读方式。验收依据仍是当前设计、真实执行结果与用户确认。

## 技术栈

Node.js / TypeScript / Vue 3 / npm Workspaces / Mermaid / Git / HTML + JSON / Host Agent Skill
