# SimsCommu：验证语音练习流程的多 Agent 应用

SimsCommu 是一个 v0.2.0 的多 Agent 口语练习 Web 应用。它已经把场景配置、角色路由、远程 STT、文本 LLM 和远程 TTS 串成可运行的练习流程；当前结论是，串行的 STT → TTT → TTS 适合验证流程，但不再是项目重启时的技术基础。

## 背景与目标

我想做一个从语音开始、以语音结束的练习应用，同时验证一条具体的工程路径：STT 负责把语音转换成文本，TTT 负责理解和生成，TTS 负责把回复合成为语音。口语练习还需要场景中的不同角色，因此项目也用于验证多 Agent 的角色调度。

## 设计与实现

主应用使用 Fastify 和 TypeScript 提供 API，React 与 Vite 负责前端。用户先配置语言、场景、用户角色和 Agent 数量，系统再通过 OpenRouter 生成角色配置并建立会话。

每轮用户文本会先交给主持人 Agent。主持人根据场景、用户角色、可用角色和历史记录选择下一位回复者，并给出路由原因；选中的角色 Agent 再生成回复。会话历史保存在主进程内存中，最多保留最近 40 条消息，并通过 WebSocket 发送路由和回复事件。

语音入口由前端录制音频，主应用把音频转发给独立的 STT 服务，再把回复文本转给独立的 TTS 服务。当前链路是串行的：语音输入完成后才进入文本处理和语音输出。

## 当前能力

- 按语言、场景、用户角色和 Agent 数量生成练习设置。
- 通过主持人 Agent 在多个角色之间选择下一位回复者。
- 创建会话、保存有限历史，并通过 WebSocket 推送路由与回复事件。
- 将录音发送到远程 STT 服务，并把回复发送到远程 TTS 服务。
- 通过 OpenRouter 按场景、模块或 Prompt ID 路由模型。
- 提供 Fastify 后端与 React 前端的开发和生产构建检查。

## 边界与取舍

当前实现依赖远程 STT、远程 TTS 和 OpenRouter 配置；会话状态保存在进程内存中，重启后不会持久化。语音链路也不支持 Live 双工交互，因此用户与 Agent 不能在同一轮中自然地互相打断。

项目是口语练习实验，不是通用客服系统，也没有把角色路由结果当作客观评价。主持人和角色回复都来自模型调用，具体质量仍受 Prompt、模型和远程服务状态影响。

## 状态与下一步

SimsCommu 当前已暂停，等待重启。现有实现与串行架构的验证结果会保留，但不会继续扩建这条链路。下一步是围绕 Live 双工模型重新设计语音主路径，再评估主持人 Agent、角色调度和练习反馈如何接入实时会话。

## 技术栈

Fastify / TypeScript / React / Vite / OpenRouter / STT / TTS / WebSocket
